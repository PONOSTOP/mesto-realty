# Frontend implementation task

Build the complete Russian real-estate frontend named «Место» using ONLY HTML CSS and browser JavaScript ES modules. Own only public/**. Parent builds backend and package setup. Do not change server, package.json, tests, or git state. Read docs/implementation-plan.md API contract section as the shared interface.

Routes served via index.html: / (home), /catalog, /property/:id, /login, /register, /account (tab=properties/favorites/profile), /publish, /edit/:id. Use real API fetches, browser history or full links; no localStorage or fake data. API uses camelCase keys. GET session obtains user and csrfToken. Every write uses X-CSRF-Token. Handle session token updates on register/login/logout. Profile user contains id,name,email,phone,bio,avatar. Public owner contains id,name,bio,avatar (no email). Images contain id,url,position. GET /api/me/properties and /api/favorites return {items,total,page,pages}. Detail returns {property,owner,images,otherProperties}. GET /api/properties/:id/contact returns phone,contactName. POST/PATCH property takes title,deal,category,city,district,address,price,area,rooms,description,contactName,contactPhone,status. Owner detail includes contactPhone. /api/profile/avatar uses multipart field avatar. POST images uses multipart images. Deletion body optional.

Design highly polished light spacious desktop and responsive mobile. Background #f7f9f8, white surfaces, ink #172d29, green #246b52. Modern system Cyrillic sans or selfhosted Manrope, generous rhythm, 3-column image cards, subtle borders and muted labels. Main hero with large architectural photo and overlaid white text «Место, где начинается ваша история», search panel overlapping bottom, sale/rent tabs, city search, category, price. Clear header wordmark, catalog links, favorite/account and publish action. Category shortcut strip and new listings from API, real city links. User did not ask map or mortgage so omit those.

Use local hero /assets/hero.webp and seed card /assets/property-1.webp etc (parent will create/download these). No externally hosted image URLs needed. You may create fallback SVG illustration in public/assets for absent photos if needed; do not draw SVG icons manually (library or text/simple CSS allowed). Actual icons can use installed @phosphor-icons/core assets later, coordinate if needed.

All required functionality: URL query filters q,deal,category,minPrice,maxPrice,minArea,maxArea,rooms,sort(newest/price_asc/price_desc),page,limit,owner. Search/filter/pagination via API. Cards include cover,price,address,area,rooms,category,isFavorite. Card heart button needs auth then toggles API. Detail gallery thumbnails, phone reveal, owner info and otherProperties. Auth forms client validation and field/server errors. Cabinet tab navigation, editable name phone bio avatar upload, own properties with status/edit/archive/delete; favorite listing. Confirm destructive delete using accessible native dialog/confirm acceptable. Publish/edit forms category-dependent rooms (required apartment/house/room, not land/commercial); required other fields minimum title 5, description 20, city 2,address 5,contactName 2, phone valid 7-15 digits, price>0 area>0; max10 photos at 8MB each, JPEG/PNG/WebP preview. Save initial object as draft, upload photos, then PATCH target status; explicit recoverable upload errors and no silent duplicate submissions. Draft need same valid fields but photographs not required. Publishing requires >=1 image server side. Edit supports deleting individual existing photos. No nonworking buttons. Land area always m² clearly labeled.

Accessibility: visible labels, errors aria-live, disabled submissions and progress, good empty/loading/error states, focus rings, keyboard navigation, reduced motion, minimum 44px targets. Escape all API/user data passed into HTML template strings and attributes; no inline event handlers; safe image URLs only server /media or /assets URLs. Keep modules reasonably split.

Parent independently works on database/backend, so frontend may initially have API unavailable. Run node --check on JS. Report files touched, implementation details and limitations in docs/frontend-report.md, send brief status when done. Do not stall for approval: user explicitly authorized full implementation.
